# DEC-20260926-002：V1 持久化数据方案（已确认）

- 关联：[REQ-20260926-003](../Requirements/REQ-20260926-003.md)、[PPD 第 5、6、9、17 节](../qsv_Web_PPD.md)。
- 状态：**已确认采用方案 A，首次迁移已执行。**2026-09-26 用户明确授权由实施者确定所有方案、确认与实施；实际结果见功能进度。
- 目标：让浏览器刷新、服务重启后仍能读取原文件、不可变版本、任务历史和模板，且按用户隔离。

## 已核对的现状

Web 前端目前仅在浏览器内存中保存演示资源和任务，没有 Web 业务数据库或真实用户数据。因此首次建库不需要历史回填、双写或在线切换。仓库 `Cargo.toml` 的 qsv 版本是 23.0.1；官方 macOS ARM64 预编译包已在临时目录通过基础核验，记录见 [ENGINE_VERIFICATION](../ENGINE_VERIFICATION.md)。本机 `rustc` 为 1.95.0，低于项目声明的 1.98 最低版本。系统 `sqlite3` 是 3.43.2，低于 PPD 对 WAL 模式要求的已修复版本；它不能作为生产数据库绑定。

## 可选方案

| 方案 | 范围与代价 |
|---|---|
| A：沿用 PPD 三表 SQLite + 文件目录（推荐） | `resources`、`jobs`、`recipes` 存有界元数据；原始文件、结果、长日志存 owner 私有目录。与现有设计、页面对象和任务恢复要求相符；需验证本机绑定版本、备份与文件提交恢复。 |
| B：仅文件目录和 JSON 清单 | 初期依赖少，但并发写入、任务领取、版本唯一性和跨对象引用都需要自建事务机制；不适合 PRD 的任务恢复与多入口写入。 |
| C：外部数据库或服务 | 可扩展部署，但增加离线安装和运维依赖，偏离 V1 单机懒猫部署目标。 |

推荐 A。浏览器只持有当前表单、选区和有界行块缓存；服务端保存实际状态。没有获批的数据模型时不会建立临时 JSON 持久化路径绕过本关口。

## 拟议实体、关系与 DDL

**拟采用 [PPD 第 5.2 节完整 SQL](../qsv_Web_PPD.md#52-建表基线) 原文作为 V1 首次建库 DDL，不增删字段或索引。** 该节逐字段列出类型、可空性、默认值、主键、唯一约束、检查约束和全部索引；本决定引用其完整 SQL，避免出现两份不同的 schema 草案。以下是执行前须确认的语义：

| 实体 | 主键与归属 | 关系及数据边界 |
|---|---|---|
| `resources` | `id` 主键；`owner_key` 必填；`(owner_key, group_id, version)` 唯一 | 每行是一个固定内容版本；`source_ids_json` 和 `producer_job_id` 保存血缘引用；大文件及完整 Schema 存在 owner 私有目录，不放入 DB。 |
| `jobs` | `id` 主键；`owner_key` 必填；`(owner_key, idempotency_key)` 唯一 | `input_ids_json` 和 `spec_json` 是提交时不可变快照；重试新建行并以 `retry_of` 指向原任务；`progress_json` 只存有界进度。 |
| `recipes` | `id` 主键；`owner_key` 必填；`(owner_key, family_id, version)` 唯一 | 修改新建版本，当前未删除版本按部分唯一索引限制每家族最多一个；旧任务不受后续修改影响。 |

PPD 草案没有跨表外键，因为有界 JSON 引用与文件清单无法由 SQLite 外键覆盖。服务层必须在事务中验证每个输入、模板与输出引用的归属和状态；物理删除前检查任务租约和有效引用。各表原始 `CHECK`、索引与 `PRAGMA` 按 PPD 第 5.2 节执行；`metadata_json` ≤64 KiB、`spec_json` ≤256 KiB、`progress_json` ≤16 KiB 的服务层上限按第 5.3 节执行。V2 的两张 AI 表不预建。

## 拟议生命周期与业务含义

- 目标归属按 PPD 使用验证后的 OIDC `(issuer, subject)` 派生，服务端用不透明 workspace ID 定位文件。当前开发阶段采用两种明确区分的模式：本机环回地址的单用户模式；懒猫模式从仅允许平台入口访问的连接读取 `X-HC-User-ID`。后一模式必须在实际部署中证明入口隔离，尚未通过真机验收。
- 相同文件名的两次上传生成不同资源 ID；原文件以只创建方式写入，不覆盖。版本号只在同一 owner 与 `group_id` 下递增；任务绑定固定 `resource.id`，界面切换版本不会修改历史任务。
- 软删除将 `status` 置为 `trashed` 并记录 `deleted_at`，默认回收期 7 天；恢复撤销标记。永久删除需先列明仍被使用的任务、模板、产物及字节数；运行中的资源不可物理删除。历史任务仍保留快照，原文不可读时明确显示。
- 任务终态不可复用；启动时将无法安全恢复的 `running`/`cancel_requested` 标为 `interrupted`。有验证过的检查点才恢复，否则重试创建新任务。幂等键相同且请求 hash 不同返回冲突。
- 上传临时文件与缓存可以清理；原文件、保留产物、任务快照和可恢复检查点不能被“清缓存”删除。

## 首次建库、升级、备份与恢复

1. 启动时核验实际 SQLite 版本为 3.51.3 或更新的已修复版本，确认持久化目录在本地文件系统且可写；不满足条件则服务不进入就绪状态。SQLite 官方说明 3.51.3 修复了 WAL-reset 问题：<https://www.sqlite.org/wal.html>。
2. 空库在独立事务中执行 PPD 第 5.2 节 DDL，并设置 `PRAGMA user_version = 1`；第二个迁移加入原文件上传幂等键的唯一索引，升级到 `user_version = 2`。版本未知或高于程序支持时拒绝启动。正式设备升级前仍需用 SQLite 在线备份和已提交资源清单生成一致快照；本机第一轮仅在开发数据上验证了版本 1→2 升级。
3. 文件输出先写私有临时路径，校验字节、记录、Schema 与 hash，`fsync` 后同文件系统 `rename`，再提交数据库 ready 状态。重启依据 `commit.json` 核对文件与数据库，登记已完成提交或回收孤儿。文件与 DB 不被视作单个原子事务。
4. 首次建库没有业务数据时可删除新库和新建目录回到空工作区；产生真实用户数据后只从一致快照恢复，不用旧程序直接打开未知新 schema，不靠删除数据库“回滚”。
