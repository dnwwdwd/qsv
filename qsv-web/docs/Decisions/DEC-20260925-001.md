## 问题与备选方向

现有 qsv 是命令行工具。Web 产品需要浏览器入口、受控执行、文件与任务持久化、用户隔离及懒猫部署。PPD 提出浏览器 SPA、Fastify API、qsv 子进程、SQLite 元数据和本地文件存储的组合；这只是待验证的实施方案。

| 方向 | 好处 | 主要代价或约束 |
|---|---|---|
| PPD 草案：独立 Web 层包装 qsv | 复用现有 CLI，不要求改动核心命令；可统一权限、任务和文件边界 | 需验证命令能力、进程开销、数据保真和持久化恢复 |
| 在 qsv Rust 程序内新增 HTTP 服务 | 可直接复用内部模块 | 会扩大上游代码改动和长期维护范围，需重新设计隔离与 API |

现阶段以 PPD 草案作为验证对象。选型是否沿用、调整或替换，以固定二进制能力测试、真实平台约束和用户确认的方案为准。

PPD 第 5 节列出拟议的 V1 `resources`、`jobs`、`recipes` 三张业务表，包含字段、类型、可空性、默认值、主键、唯一与检查约束及索引；第 5.4 节列出 V2 的 `ai_sessions`、`ai_events` 增量设想。第 6、9、17 节涉及文件一致性、任务恢复、备份与有序迁移。这些内容均标记为**待确认设计**，尚未写入本仓库的 schema 或 migration。
